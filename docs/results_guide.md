# Results interpretation guide

This document helps researchers interpret the various output artifacts generated by this repository and avoid common pitfalls.

## Canonical vs. Reviewer results

| Feature | Canonical (`heavy_r1`) | Reviewer Revision |
|---------|------------------------|-------------------|
| **Goal** | Main manuscript claims | Address specific reviewer concerns |
| **Location** | `analysis/manuscript_canonical/` | `analysis/reviewer_revision/` |
| **Scope** | All traces, standard splits | Targeted subsets/ablations |
| **Baseline** | Classical + LRB | Extended Fairness Retraining |

**Warning**: Do not compare `heavy_r1` miss ratios directly against reviewer ablation results unless they share the exact same trace range and scoring window.

## Miss ratio metrics

We report miss ratios across two primary windows:

1. **Full-stream**: The miss ratio across the entire trace (including the warm-up period).
2. **Scoring window**: The miss ratio on the held-out test segment (typically the last 20% of the trace).

Learned policies (`evict_value_v1`) are optimized for the **scoring window**. Comparisons against classical baselines (LRU, Belady) are most fair within this window.

## Oracle bounds

- **Offline Belady**: The optimal eviction policy for unweighted paging (MIN). It provides a theoretical lower bound on the miss ratio.
- **Offline General Caching LP**: The approximate optimum for variable-size/cost caching.

If a learned policy outperforms Belady, it usually indicates a bug in the simulator or an overlap between training and testing data.

## Common pitfalls

### 1. Direct comparison of different capacities
Always ensure that policies are compared at the **same cache capacity (k)**. A policy with `k=128` will almost always outperform one with `k=32`.

### 2. Sensitivity grid variants
The `analysis/exploratory/` directory often contains large sweeps over hyperparameters. These are intended for diagnostic purposes and should not be used as primary evidence for policy superiority unless explicitly stated.

### 3. Trace versioning
Ensure you are using the `data/processed/` standardized traces. Results obtained on raw or ad-hoc filtered traces are not reproducible via the canonical pipeline.

## Provenance verification

Every `report.md` or `summary.json` in the `analysis/` directory contains a `provenance` section. Before citing a result, verify:
- The `protocol_id` matches the expected experiment.
- The `git_hash` corresponds to the version of the code used.
- The `scoring_window` matches the manuscript's convention.
